Week 8 — Guided Lab (35 min)

Walk an OIDC redirect, prove your validator works, then put OAuth in front of last week's MCP server.

Scope: a local protocol/claims demonstration, not real-provider login, session logout or a production authorization boundary. Use provider integration for the separate HW7 positive path. Every student operates their own processes and accounts.

Start commands: the demo runbook covers every server, client, expected result and cleanup step. It also starts the complete browser application, local provider and authenticated resource server with one command after installation. Use that path to see a working sign-in and session, rather than treating the parameter builder below as a complete web application.

What you leave with: six terminal transcripts, all of which are required HW7 evidence. Redirect output to a file as you go and a third of the homework is done before you leave the room.

Part 1 — Read a real provider, then build the request (5 min)

1.1 Read a real provider's configuration

curl -s https://accounts.google.com/.well-known/openid-configuration

Find and write down four fields: issuer, authorization_endpoint, jwks_uri, code_challenge_methods_supported.

Notice two things. The token endpoint is on a different host from the issuer (oauth2.googleapis.com, not accounts.google.com) — which is why you never hardcode it. And code_challenge_methods_supported includes plain. A major provider still accepts the weak PKCE method for backwards compatibility. You must not choose it.

Then count the keys:

curl -s https://www.googleapis.com/oauth2/v3/certs

Count the keys actually returned; the count changes during rotation. Selecting keys[0] works only by accident. Offline? fixtures/discovery-google.json and fixtures/jwks-google.json are snapshots taken 2026-08-15.

1.2 Build a PKCE pair and a complete authorization URL

node pkce.mjs 2>&1 | tee out/part1-pkce.txt

PowerShell:

node pkce.mjs 2>&1 | Tee-Object -FilePath out\part1-pkce.txt

Expected: the discovered endpoints, a code_verifier, a code_challenge, and an authorization URL carrying code_challenge_method=S256, state, nonce, and resource.

Inspect the URL as text. This helper starts no callback listener and does not establish a browser session. Do not interpret an unserved http://127.0.0.1:5173/callback as a completed login. Part 2 performs a real successful code exchange before testing replay; the complete browser demo performs the actual redirect, callback, validation and session creation.

Append &login_as=operator to the authorization URL to sign in as the operator instead of the viewer. That one parameter is this lab's entire identity provider; use the real-provider handoff in HW7, not this mechanism in your app.

Part 2 — Prove PKCE and single-use codes do something (3 min)

node pkce-negative.mjs 2>&1 | tee out/part2-pkce-negative.txt

Expected — four results:

--- 1. exchange with the WRONG code_verifier -------------------
HTTP 400
{ "error": "invalid_grant",
  "error_description": "PKCE verification failed: S256(code_verifier) != code_challenge",
  "expected_challenge": "z_1m6MhVmoJag5sEMKeOZYshyxGMEGMJ5lHhsRzUDyg",
  "computed_challenge": "S8PQCZIMviVjOxZP2iqQH5p7gAQgZkWZjGWqrDhwH4E" }

--- 2. the RIGHT verifier, on that same code -------------------
HTTP 400  { "error": "invalid_grant",
            "error_description": "unknown or already-redeemed code" }

--- 3. a clean code, correct verifier, then replayed -----------
HTTP 200  {"token_type":"Bearer","expires_in":900,"scope":"openid campuspulse.read"}
HTTP 400  {"error":"invalid_grant","error_description":"unknown or already-redeemed code"}

--- 4. an authorization request with no PKCE at all ------------
HTTP 400
  invalid_request Missing: code_challenge , code_challenge_method …

Result 2 is the one to think about. This server consumed the code on the failed attempt, so the honest client cannot recover either. RFC 7636 §4.6 only requires that the wrong verifier be rejected; RFC 6749 §4.1.2 makes codes single-use; RFC 9700 §2.1.1 pushes toward treating a failed redemption as an attack signal. Providers differ — testing yours is an HW7 line item. The reasoning for the strict choice: a wrong verifier means somebody other than your client is holding the code, and a retry for the honest client is also a retry for the attacker.

Part 3 — Decode, then actually validate (8 min)

3.1 Decode. Notice that you have proved nothing.

node validate-token.mjs --variant valid --decode-only

You get a header and a payload. You have base64-decoded a string. No claim on that screen has been verified.

3.2 Run the eight checks

node validate-token.mjs --variant valid --scope campuspulse.read \
  2>&1 | tee out/part3-valid.txt

Expected: eight PASS lines, then ACCEPT 200.

3.3 Tamper with the payload and watch it fail

Change one claim without touching the signature. This is the whole lesson.

node tamper.mjs
node validate-token.mjs --token-file out/forged.txt --scope campuspulse.incident.write \
  2>&1 | tee out/part3-tampered.txt

tamper.mjs mints a genuine viewer token, rewrites roles to ["operator"] and adds the write scope, re-encodes the payload, and leaves the signature untouched. It prints exactly what it changed.

Expected:

  PASS  alg is on the allow-list
  PASS  kid resolves in JWKS
  FAIL  signature verifies      cryptographic verification failed
REJECT 401  error_description="signature verification failed"

The decoder happily shows "roles": ["operator"]. The validator rejects it at check 3. Decoding is a display operation. Validation is a security operation.

Part 4 — Rotation, and a key you have never seen (2 min)

Skip this part first if you are short on time. It is the shortest and the least load-bearing.

curl -s http://127.0.0.1:9100/rotate

The response lists both kids: the new active one and the previous one, still published. That is what a well-run rotation looks like — old keys stay in the JWKS until every token signed with them has expired. Confirm a fresh token still validates:

node validate-token.mjs --variant valid --scope campuspulse.read

Now force the other outcome — a token signed by a key that is not published:

node validate-token.mjs --variant stale-kid

Expected:

  PASS  alg is on the allow-list
  FAIL  kid resolves in JWKS   kid=retired-2025-key not among [ … ]
  FAIL  signature verifies     cryptographic verification failed
REJECT 401  error_description="unknown signing key"

The 3am version of this: your provider rotates and removes the old key while your service is holding a JWKS it cached with no TTL and no refresh-on-miss. Every valid token in production starts failing. Nothing was deployed. Same shape as the Week 1 certificate-expiry story.

The proxy in Terminal 2 implements both rules — a 5-minute TTL and a refetch when a kid misses. Read getKey() in mcp-auth-proxy.mjs; it is fifteen lines and it is the difference between surviving a rotation and paging someone.

Part 5 — Put OAuth in front of your MCP server (10 min)

5.1 The refusal that starts the protocol

curl -i -X POST http://127.0.0.1:8930/mcp \
  -H 'content-type: application/json' \
  -H 'accept: application/json, text/event-stream' \
  -H 'Mcp-Method: tools/call' \
  -H 'Mcp-Name: post_incident_update' \
  -H 'Mcp-Protocol-Version: 2026-07-28' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"post_incident_update"}}'

PowerShell:

try {
  Invoke-WebRequest -Uri http://127.0.0.1:8930/mcp -Method POST -ContentType application/json `
    -Headers @{'Mcp-Method'='tools/call';'Mcp-Name'='post_incident_update';'Mcp-Protocol-Version'='2026-07-28'} `
    -Body '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"post_incident_update"}}'
} catch { $_.Exception.Response.StatusCode; $_.Exception.Response.Headers['WWW-Authenticate'] }

Expected:

HTTP/1.1 401 Unauthorized
www-authenticate: Bearer resource_metadata="http://127.0.0.1:8930/.well-known/oauth-protected-resource", scope="campuspulse.incident.write"

Note the scope in the challenge: the server names what this operation needs, not everything it supports, so the client can request least privilege. Try the same call with Mcp-Name: list_service_status and watch the scope hint change.

Then follow the pointer:

curl -s http://127.0.0.1:8930/.well-known/oauth-protected-resource

{
  "resource": "http://127.0.0.1:8930/mcp",
  "authorization_servers": ["http://127.0.0.1:9100"],
  "scopes_supported": ["campuspulse.read", "campuspulse.incident.write"],
  "bearer_methods_supported": ["header"]
}

That is RFC 9728, and MCP specification 2026-07-28 makes publishing it a MUST.

What is not in that document: the authorization server's jwks_uri. In RFC 9728 the jwks_uri field means "keys this resource signs its own responses with" — not the token-signing keys. A client finds those by following authorization_servers and reading that server's metadata. Publishing the AS's JWKS here is a common and confusing mistake.

5.2 The whole progression, automated

node mcp-client-walk.mjs 2>&1 | tee out/part5-viewer-read.txt

Expected final lines:

[7] tools/call list_service_status WITH the access token
    HTTP 200
    body: {"result":{"content":[{"type":"text","text":"{\n  \"generatedAt\": …

======================================================================
RESULT  401 -> 200. The same call, the same server, one credential apart.
======================================================================

If the body says "stub": true, your Week 7 server is not reachable — see troubleshooting. The authorization result is still valid evidence.

5.3 Per-tool scope: deny, then allow

node mcp-client-walk.mjs --tool post_incident_update \
  2>&1 | tee out/part5-viewer-write-denied.txt

node mcp-client-walk.mjs --tool post_incident_update --login-as operator \
  2>&1 | tee out/part5-operator-write-allowed.txt

Expected — the viewer:

    scope=openid campuspulse.incident.write
           ^ from the WWW-Authenticate challenge — least privilege
    …
    scope         openid                  <- the tenant refused to grant the write scope
[7] HTTP 403
    WWW-Authenticate: Bearer error="insufficient_scope",
      scope="campuspulse.incident.write",
      resource_metadata="http://127.0.0.1:8930/.well-known/…"
RESULT  401 -> 403. Authentication succeeded; authorization did not.

Expected — the operator:

    scope         openid campuspulse.incident.write
[7] HTTP 200
    body: {"result":{"content":[{"type":"text","text":"{\n \"posted\": true,
           \n \"ref\": \"INC-2026-0016\", \n \"feedEventId\": 1001\n}"}] …
RESULT  401 -> 200.

Three things happened, and you should be able to name all three:

  1. The client asked for only the scope named in the 401 challenge — least privilege, driven by the server.
  2. The authorization server refused to grant the viewer the write scope at all, because the user is not an operator. Requested and granted scope differ in the token response. That is the scope × role intersection, visible as data.
  3. The proxy then refused the call, and named the missing scope in the challenge so a well-behaved client could step up.

There is a second gate you did not trigger. post_incident_update requires the write scope and the operator role (see the policy table the proxy printed at startup). A token with the write scope but a viewer role gets 403 insufficient_permission — and, unlike insufficient_scope, that one has no scope hint, because no amount of re-authorizing fixes it. Only an administrator can.

5.4 Read your audit log

Look at Terminal 2. One JSON line per decision:

{"ts":"2026-08-15T20:47:20.047Z","decision":"deny","status":403,
 "reason":"insufficient_scope","required":"campuspulse.incident.write",
 "granted":["openid"],"method":"tools/call","name":"post_incident_update",
 "args":["body","confirm","isPublic","ref"],
 "sub":"a4f1c0de-…","jti":"03318502-…"}

actor → tool → argument shape → decision → result, with jti so a specific credential is traceable. Note args: argument names only, never values. An audit log full of argument values is a copy of your database with a search box on it. Week 9 grades this log. Copy your own lines into out/part5-audit.jsonl.

5.5 Try to bypass the proxy

curl -s -X POST http://127.0.0.1:8931/mcp \
  -H 'content-type: application/json' \
  -H 'accept: application/json, text/event-stream' \
  -H 'Mcp-Method: tools/list' \
  -H 'Mcp-Protocol-Version: 2026-07-28' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientInfo":{"name":"bypass","version":"1.0.0"},"io.modelcontextprotocol/clientCapabilities":{}}}}'

PowerShell:

$body = '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientInfo":{"name":"bypass","version":"1.0.0"},"io.modelcontextprotocol/clientCapabilities":{}}}}'
(Invoke-WebRequest -Uri http://127.0.0.1:8931/mcp -Method POST -ContentType application/json `
  -Headers @{'Mcp-Method'='tools/list';'Mcp-Protocol-Version'='2026-07-28'} -Body $body).Content.Substring(0,200)

It works, with no token. (If you get -32602 … missing _meta, you dropped part of the envelope — spec revision 2026-07-28 requires it on every request.)

The proxy is a perimeter control and the perimeter has a hole in it. In the lab, port 8931 binds to loopback so only you can reach it. In your deployment that has to become a network policy, or the check has to move inside the server. HW7 asks you to say which you chose and why.

Part 6 — Where Week 7 and Week 8 collide (3 min)

An access token lives fifteen minutes. A subscriptions/listen stream lives for hours, and takes one authorization decision — at open.

Reproduce the bug. In Terminal 2, stop the proxy and restart it unenforced:

# bash
ENFORCE_STREAM_EXPIRY=0 node mcp-auth-proxy.mjs

# PowerShell
$env:ENFORCE_STREAM_EXPIRY='0'; node mcp-auth-proxy.mjs

Then:

node expiry-mid-connection.mjs --ttl 6 --watch 14 2>&1 | tee out/part6-bug.txt

Expected:

t+  0s  open        {"exp":1786824030,"expires_in":6,"enforcing":false}
t+  6s  heartbeat   {"n":3,"token_expires_in":0,"still_streaming":true}
t+  8s  heartbeat   {"n":4,"token_expires_in":-2,"still_streaming":true}
t+ 12s  heartbeat   {"n":6,"token_expires_in":-7,"still_streaming":true}

t+ 14s  watch window over — the stream is STILL OPEN.

Now the fix. Restart the proxy normally (node mcp-auth-proxy.mjs) and re-run:

node expiry-mid-connection.mjs --ttl 8 --watch 22 2>&1 | tee out/part6-fixed.txt

Expected:

t+  6s  heartbeat      {"n":3,"token_expires_in":2,"still_streaming":true}
t+  8s  token_expired  {"error":"invalid_token",
                        "error_description":"access token expired; re-authorize and reconnect"}

t+  8s  stream CLOSED by the authorization proxy at token expiry.

Both transcripts are required HW7 evidence. The homework asks you to document the behaviour you observed, not the behaviour you intended.

Troubleshooting

1. Every token is rejected with unknown signing key

Cause, almost always: you restarted the authorization server. It mints a brand-new RSA key at startup, so every token issued by the previous run is now signed by a key that no longer exists.

Fix: get a fresh token — re-run whichever script produced the one you are using. The proxy re-fetches the JWKS when it meets an unknown kid, so it heals itself; the token is the stale thing, not the proxy.

If the authorization server is down, you will instead see unknown signing key on every request because the JWKS fetch fails. Check:

curl -s http://127.0.0.1:9100/jwks.json

This is a real production failure mode reproduced accidentally. If it bit you, note it in your HW7 AI-use log.

2. upstream_unavailable / ECONNREFUSED 127.0.0.1:8931

Your Week 7 MCP server is not running. Two options:

# preferred — fix the real thing
cd ../../../samples/mcp-starter && npm run start:http

# unblock now, fix later
MCP_UPSTREAM=stub node mcp-auth-proxy.mjs      # bash
$env:MCP_UPSTREAM='stub'; node mcp-auth-proxy.mjs   # PowerShell

stub mode answers the shape of an MCP response so every authorization result in Part 5 is still real and still submittable. Say in your write-up that you used it.

3. EADDRINUSE on 8930, 8931, or 9100

Something is already listening — often a previous run of this lab.

# macOS / Linux
lsof -ti tcp:8930 | xargs kill

# Windows PowerShell — find the PID, then stop that specific process
Get-NetTCPConnection -LocalPort 8930 -State Listen | Select-Object OwningProcess
Stop-Process -Id <PID> -Force

Or move the port: PORT=8940 node mcp-auth-proxy.mjs — but then the resource identifier changes, so also set MCP_RESOURCE=http://127.0.0.1:8940/mcp on the proxy and the authorization server, or every token fails audience validation. That is itself a useful thing to see once.

What this lab deliberately does not do

  • No TLS. Everything is loopback HTTP so you can read it with curl -i. Real deployments require HTTPS everywhere; MCP specification 2026-07-28 assumes it.
  • No client authentication at the lab token endpoint. A confidential client would authenticate; a public client uses PKCE alone.
  • No introspection path. The proxy validates JWTs offline. The MCP authorization tutorial uses Keycloak introspection instead — both are correct, with the tradeoff from Block B.
  • The lab authorization server is not an identity provider. "Login" is a query parameter. Use the course tenant for anything you would describe as authentication.
